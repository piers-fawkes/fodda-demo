# Clerk support ticket — paste into Clerk Dashboard → Support

**Subject:** Production Account Portal `/oauth-consent` renders a blank page — all OAuth authorize flows dead-end

**Instance:** production, application domain `fodda.ai` (Frontend API `clerk.fodda.ai`, Account Portal `accounts.fodda.ai`)

**Summary**
The Account Portal's OAuth consent route is not rendering. `https://accounts.fodda.ai/oauth-consent?...`
(with the exact parameters generated by your own `/oauth/authorize/continue` handoff) loads the
portal shell and the `oauth-consent` route chunk, then makes **zero Frontend API requests** and
renders an **empty body**. It also does not redirect signed-out visitors to sign-in. Other portal
routes are fine — `https://accounts.fodda.ai/sign-in` renders normally (loads its route chunk,
clerk-compat, and CSS).

Because our OAuth applications are created via dynamic client registration (Claude / MCP
connector directory), the consent screen is enforced and every authorization flow funnels
through this broken route — so all connector authorizations currently dead-end and users are
stranded on our after-sign-in fallback instead of returning to the OAuth client.

**Reproduction**
1. Register a client via DCR: `POST https://clerk.fodda.ai/oauth/register` with
   `{"client_name":"debug","redirect_uris":["https://claude.ai/api/mcp/auth_callback"]}`.
2. Open `https://clerk.fodda.ai/oauth/authorize?response_type=code&client_id=<id>&redirect_uri=https%3A%2F%2Fclaude.ai%2Fapi%2Fmcp%2Fauth_callback&scope=openid%20email%20profile&state=x&code_challenge=<S256>&code_challenge_method=S256`
   in a browser with no session. Observe the 302 chain ends at
   `app.fodda.ai?redirect_url=https%3A%2F%2Faccounts.fodda.ai%2Foauth-consent%3F...` (expected).
3. Open that inner `accounts.fodda.ai/oauth-consent?...` URL directly (signed-out) — blank page,
   no API calls, no redirect. Signed-in users report the same flow depositing them back on
   `app.fodda.ai` (the configured home/after-sign-in URL) with the transaction never completed.

Observed 2026-08-26/27 (ET), from both a real Chrome profile and a clean automated browser.
Asset loads observed on the blank route: `assets/index-B4SHO8Ja.js`,
`assets/oauth-consent_._-DxsbMHe4.js` (small re-export stub) — and nothing further. Console shows
only a CSP block of `vercel.live/_next-live/feedback/feedback.js`.

**Timeline / impact**
Connector authorizations completed successfully in prior weeks ("Allow" screen shown, redirect
back to the client). First user-reported failures 2026-08-26 morning ET; 100% of attempted
connector connects since then have failed to return to the client.

**Questions**
1. Is there a known issue/regression on the Account Portal `oauth-consent` route (new
   TanStack-based portal)?
2. Is the raw-parameter consent URL (as generated by the sign-in handoff `redirect_url`) still a
   supported re-entry point, or does the route now require server-side transaction context?
3. Anything instance-specific you can see in our Application Logs around
   `oauth_authorization.*` events for 2026-08-26?

**Mitigation on our side**
We are deploying a custom consent page (Dashboard → Paths → Component paths → OAuth consent →
`https://app.fodda.ai/oauth-consent`) rendering the prebuilt `<OAuthConsent />` from
`@clerk/react` 6.7.2. Please confirm that is the recommended interim path and whether any
portal-side fix would conflict with it.
